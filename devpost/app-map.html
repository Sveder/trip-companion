Trip Companion: app map

A one-page guide to where things live in the code. Made from commit 6a53ee3 on 2026-10-09.

This map is a snapshot. The code keeps changing, so a path or a name here can drift. Check the source when in doubt.

1. What the app does

Trip Companion gets a family ready for a trip to Japan. The family puts its people on a plane, the app picks short activities that fit those ages, and the family does one activity at a time: picture lessons, words, manners, safety and a Street View hunt. A short quiz brings back what they met. In Japan, a photo list and a highlights page keep the memories. It works on a phone, a laptop and a TV browser, in English and in Hebrew.

  • Accountsaccounts/ Email sign-in with a one-time code (django-allauth), no password.
  • Tripstrips/ The trip: the place, the length and the people on the plane.
  • Coursescourses/ Picks the modules that fit the family and puts the activities in order.
  • Activities and contentactivities/, content/japan/*.yaml One YAML file per module holds the pages; templates show each kind.
  • Practicepractice/ A small quiz with Leitner boxes. Things the family met come back later.
  • There and highlightsthere/, courses/highlights.py The "while you are there" photo list and the highlights page.
  • Remindersreminders/ Email nudges for the next activity, with an unsubscribe link.

3. The route through the code reference route, not toured

Search for the anchor in each file. The anchors are names, not line numbers, so they survive small edits.

  1. templates/activities/lesson.html, search data-spots. The server renders every page of the lesson from content/japan/food.yaml (the sushi-lesson entry, page kind: spots, "Tap the plate"). Each dot is a button with data-spot; its text sits in a data-spot-info box.
  2. static/js/lesson.js, search function setupSpots and function placeSpots. placeSpots puts the number badges beside the picture and draws the lines. setupSpots listens for a tap, shows the matching info text and updates the "found" count. Nothing goes to the server here.
  3. activities/views.py, search def activity_done, then practice/items.py, search def add_items and def quiz_entries. Done marks the activity as finished and calls add_items. For a lesson, quiz_entries takes the spot and flip cards, one page at a time, and add_items stores a PracticeItem (practice/models.py) for each new one. practice/views.py def quiz then asks the due items, and PracticeItem.answer sets the next date.
Where the tests for this route live

practice/tests.py: LessonQuizTests (for example test_finishing_the_lesson_adds_at_most_twelve_items and test_spot_question_in_english_and_hebrew) and LeitnerTests (the box intervals). Run them with venv/bin/python manage.py test practice.

5. A practice to reuse

Check the real device's browser before the real-device test. The family TV in the test is an LG webOS 6 set, and its browser is Chrome 87. That browser has no CSS aspect-ratio and no :has(). On the TV the trip-setup plane was 0 px tall and the builder switches all looked off, while every desktop check was green.

The fix had two parts. Each new-only CSS feature got a twin that old browsers understand: a ::before spacer for the height, and a class set by static/js/compat.js for each :has() rule. Then a script removed those features from a normal browser and measured the pages again, before anyone touched the TV.

Reference: devpost/checklist.md, under ## Revisions, the line that starts "2026-10-08, T101". On another project: find out the oldest browser the users really have, look up its version, and run one check with the new features switched off.

6. Run it again

python3 -m venv venv
venv/bin/pip install -r requirements.txt
venv/bin/python manage.py migrate
venv/bin/python manage.py load_content japan
venv/bin/python manage.py runserver
